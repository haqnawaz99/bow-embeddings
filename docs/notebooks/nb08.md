## From Search to Answers

FAISS retrieves the most relevant passages. But a user asking *"What does the text say about patience in hardship?"* doesn't want 5 paragraphs to read through — they want a direct, cited answer.

RAG (Retrieval-Augmented Generation) bridges this gap. It:
1. **Retrieves** relevant passages using semantic search
2. **Augments** a prompt with those passages as context
3. **Generates** a grounded, cited answer using an LLM

---

## The Three Stages

```
User Query
    |
    v
[ RETRIEVE ]
  encode query → 384-dim vector
  FAISS IndexFlatIP → top-k passages with scores
    |
    v  passages + verse IDs
[ AUGMENT ]
  wrap passages with [Surah:Verse] citation tags
  truncate long passages (max 450 chars)
  cap total context (max 2,200 chars)
  prepend grounding instructions
    |
    v  structured prompt
[ GENERATE ]
  tokenize prompt (truncate to 512 tokens)
  flan-t5-small → beam search → output tokens
  decode to text
    |
    v
  Grounded answer with citation tags
```

## Stage 1: Retrieve

The `encode_query_vec` function is exposed as a standalone function — students can call it directly to inspect the query vector before retrieval:

```python
def encode_query_vec(query):
    """Encode a query string to a normalized float32 FAISS-ready vector."""
    vec = st_model.encode([query], normalize_embeddings=True).astype(np.float32)
    return np.ascontiguousarray(vec)

# Inspect the query vector
vec = encode_query_vec("mercy and forgiveness")
print("Shape:", vec.shape)          # (1, 384)
print("L2 norm:", np.linalg.norm(vec))  # 1.0 — confirms normalization
```

The `retrieve` function returns structured result dicts with rank, verse_id, text, and score:

```python
def retrieve(query, k=TOP_K):
    vec = encode_query_vec(query)
    scores, indices = index_flat.search(vec, k)
    return [
        {"rank": rank, "verse_id": row["verse_id"],
         "text": row["daryabadi"], "score": float(score)}
        for rank, (idx, score) in enumerate(zip(indices[0], scores[0]), 1)
        for row in [df.iloc[idx]]
    ]
```

## Stage 2: Augment (Prompt Building)

The prompt must tell the model:
- What context it has access to
- What question to answer
- That it should cite passages and admit uncertainty

```python
SYSTEM_PROMPT = (
    "You are a careful assistant. "
    "Use ONLY the context passages below to answer the question. "
    "Cite the verse IDs (e.g. [4:36]) when you make a claim. "
    "If the context does not contain the answer, say: "
    "'I cannot tell from the provided context.'"
)

def build_rag_prompt(query, retrieved):
    # Wrap each passage with its citation tag
    blocks = ["[" + h["verse_id"] + "] " + h["text"][:VERSE_MAX_CHARS]
              for h in retrieved]
    context = "\n\n".join(blocks)[:CONTEXT_MAX_CHARS]

    return (SYSTEM_PROMPT
            + "\n\n--- Context ---\n" + context
            + "\n\n--- Question ---\n" + query
            + "\n\n--- Answer ---\n")
```

**Why two levels of truncation?**

- Per-passage truncation (450 chars): prevents one long verse from consuming the entire context budget
- Total context cap (2,200 chars): keeps the full prompt under the model's 512-token input limit

## Stage 3: Generate

We use `google/flan-t5-small`:

| Property | Value |
|---|---|
| Architecture | Seq2Seq transformer (encoder-decoder) |
| Parameters | ~80 million |
| Download size | ~300 MB |
| Max input | 512 tokens |
| Max output | 96 new tokens (configurable) |
| Search strategy | Beam search (num_beams=2) |
| Hardware | CPU — no GPU needed |

```python
def generate_answer(prompt):
    inputs = gen_tokenizer(
        prompt, return_tensors="pt",
        truncation=True, max_length=512
    ).to(DEVICE)
    with torch.no_grad():
        output_ids = gen_model.generate(
            **inputs,
            max_new_tokens=MAX_NEW_TOKENS,
            num_beams=NUM_BEAMS,
            early_stopping=True,
        )
    return gen_tokenizer.decode(output_ids[0], skip_special_tokens=True)
```

Set `USE_LOCAL_LLM = False` in the config cell to skip the generator download and run retrieval only.

## RAG vs No-Context Comparison

The same query is run through two conditions:

**No-context (baseline):**
```
prompt = "Answer the following question: " + query
```
The model draws only on parametric memory — knowledge baked into its weights. For a small model like flan-t5-small, this often produces vague, generic, or hallucinated answers.

**RAG (with context):**
The model receives the top-k retrieved passages. The answer should be more specific, faithful to the corpus, and citable.

The gap between the two answers illustrates exactly why RAG was proposed: it shifts the burden from "what did the model memorize?" to "what does the retrieved evidence say?"

## What This Notebook Is NOT

This is a teaching prototype — intentionally minimal. Before building on it, understand what it deliberately omits:

| Missing piece | Why it matters |
|---|---|
| Re-ranking | Top-k by cosine alone can include off-topic passages |
| Faithfulness evaluation | No way to verify the answer is grounded in the context |
| Grounding check | The model may answer from memory and ignore the context |
| Safety filters | No hallucination detection, toxicity check, or output validation |
| Evaluation suite | No NDCG, no RAGAS, no human eval |
| Conversation history | Single-turn only — follow-up questions lose all context |
| Production indexing | IndexFlatIP over 2,500 verses is fine for demo; millions of docs need IVF or HNSW |

All of these are addressed in NB09.
