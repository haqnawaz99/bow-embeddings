## The Problem with Word Averaging

Word2Vec and FastText produce one vector per word. To represent a sentence, the standard approach is to average the word vectors. But averaging has a fundamental flaw: it destroys word order, grammar, and composition.

```
"The dog bit the man"
average([dog, bit, man]) = v

"The man bit the dog"
average([man, bit, dog]) = v   ← identical!
```

Two sentences with opposite meanings produce **the same** mean vector. And:

```
"not good"  → average([good]) = [0.4, -0.2, ...]
"not bad"   → average([bad])  = [-0.3, 0.5, ...]

# The "not" was a stopword and got removed.
# The negation is invisible in the averaged representation.
```

What we need is a model trained to produce a single vector for an entire sentence, where the vector captures the sentence's **meaning as a whole** — not just the average of its parts.

---

## SBERT Architecture

**SBERT (Sentence-BERT)**, introduced by Reimers & Gurevych in 2019, fine-tunes a BERT-based transformer to produce sentence-level embeddings by:

1. Processing the full sentence through a transformer (BERT or RoBERTa)
2. **Mean pooling** the token representations (not just the [CLS] token)
3. Fine-tuning on **sentence pairs** labeled as similar/dissimilar (Natural Language Inference datasets)

### Why not just use BERT?

Regular BERT can be used as a sentence encoder — but it was not trained for this purpose. Comparing two BERT sentence embeddings with cosine similarity gives poor results. SBERT is explicitly optimized to make semantically similar sentences produce similar vectors.

```
BERT (not fine-tuned for sentence similarity):
  cosine("I love dogs", "Puppies are wonderful") = 0.34  ← weak

SBERT (fine-tuned on NLI pairs):
  cosine("I love dogs", "Puppies are wonderful") = 0.78  ← strong
```

### SBERT vs BERT

| Property | BERT | SBERT |
|---|---|---|
| Training objective | Masked language modeling | Sentence pair similarity |
| Output | Token embeddings | Sentence embedding |
| Comparison speed | Slow (cross-encoder) | Fast (pre-computed) |
| Use case | NLU tasks | Semantic search, clustering |

## The Model: all-MiniLM-L6-v2

We use `all-MiniLM-L6-v2` from the `sentence-transformers` library:

| Property | Value |
|---|---|
| Architecture | MiniLM (distilled from larger transformer) |
| Parameters | 22 million |
| Embedding dimensions | 384 |
| Max sequence length | 256 tokens |
| Training data | 1 billion+ sentence pairs |
| Speed | ~14,000 sentences/sec on CPU |

It is one of the best small models for semantic similarity tasks — fast enough to run on CPU while maintaining strong quality.

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")
embeddings = model.encode(
    sentences,
    batch_size=64,
    normalize_embeddings=True,  # L2 normalize → dot product = cosine similarity
    show_progress_bar=True,
)
```

---

## Why L2 Normalisation?

Cosine similarity between vectors A and B:
```
         A · B
cos(θ) = ─────────
         |A| × |B|
```

If both vectors are L2-normalized (length = 1), the denominator equals 1, so:
```
cos(θ) = A · B   (just a dot product)
```

FAISS `IndexFlatIP` computes inner products. So: normalize embeddings → use `IndexFlatIP` → you get exact cosine similarity. This is the standard pattern throughout NB06–NB09.

## SBERT vs TF-IDF: When Each Wins

| Query type | Better method | Why |
|---|---|---|
| Exact keyword ("day of resurrection") | TF-IDF | Exact match — TF-IDF is precise |
| Semantic ("hardship and endurance") | SBERT | Finds synonyms and paraphrases |
| Proper nouns ("Moses", "Pharaoh") | TF-IDF | Rare terms → high IDF, exact match |
| Conceptual ("divine compassion") | SBERT | Captures concept regardless of vocabulary |
| Short single words | TF-IDF | Less ambiguity, exact works fine |
| Long natural language queries | SBERT | Full sentence semantics captured |

This is why NB09 uses **hybrid retrieval** — both methods together.

## Limitations

**1. Max sequence length truncation**
`all-MiniLM-L6-v2` truncates at 256 tokens. Long verses are cut off — the tail of the verse is invisible to the encoder.

**2. Computational cost**
Encoding 6,236 verses takes several minutes on CPU. For millions of documents, batch encoding on GPU becomes necessary.

**3. Domain mismatch**
The model was trained on general English text. Classical, formal language (like translations of religious texts) may produce lower-quality embeddings than the model produces on modern conversational text.

**4. Black-box similarity**
A high cosine score does not tell you *why* two sentences are similar. You cannot inspect which words drove the similarity.

**5. No explicit reasoning**
SBERT finds the most similar passages — it cannot reason about them, compare them, or synthesize an answer. That requires a generative model (RAG — NB08).
