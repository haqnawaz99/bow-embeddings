## The Scaling Problem

In NB06, we compute cosine similarity between the query vector and **every** verse vector. With 6,236 verses, this takes milliseconds. But what about 1 million documents? 100 million?

Brute-force similarity search scales linearly with corpus size:

```
6,236 verses      → ~5 ms per query     (fine)
100,000 verses    → ~80 ms per query    (acceptable)
1,000,000 verses  → ~800 ms per query   (too slow)
100,000,000 docs  → ~80,000 ms = 80s    (unusable)
```

We need an **index structure** that makes nearest-neighbour search sub-linear.

---

## FAISS

**FAISS** (Facebook AI Similarity Search) is a library for efficient similarity search over large collections of dense vectors. It supports both exact and approximate search, and can handle billions of vectors.

---

## IndexFlatIP — Exact Search

`IndexFlatIP` is the simplest FAISS index. It stores all vectors and performs exact inner-product (dot product) search — equivalent to exact cosine similarity when vectors are L2-normalized.

```python
import faiss
import numpy as np

d = embeddings.shape[1]  # 384 dimensions

index = faiss.IndexFlatIP(d)
index.add(np.ascontiguousarray(embeddings, dtype='float32'))

# Search for top-5 most similar to query
scores, indices = index.search(query_vec, k=5)
```

!!! note "np.ascontiguousarray"
    FAISS requires vectors to be in C-contiguous memory order (row-major). Always wrap arrays with `np.ascontiguousarray(arr, dtype='float32')` before calling `index.add()` to prevent silent memory bugs.

**When to use:** Any corpus under ~100K vectors where exact results matter. Fast enough for this workshop.

---

## IndexIVFFlat — Approximate Search

`IndexIVFFlat` (Inverted File with Flat sub-quantizer) makes search faster by **partitioning** the vector space:

1. **Training:** k-means clusters the corpus into `nlist` Voronoi cells
2. **Indexing:** Each vector is assigned to its nearest cell centre
3. **Search:** At query time, only search the nearest `nprobe` cells

```python
nlist = 50   # number of Voronoi cells
nprobe = 8   # number of cells to search at query time

quantiser = faiss.IndexFlatIP(d)
index_ivf = faiss.IndexIVFFlat(quantiser, d, nlist, faiss.METRIC_INNER_PRODUCT)

index_ivf.train(embeddings)   # required — runs k-means clustering
index_ivf.add(embeddings)
index_ivf.nprobe = nprobe

scores, indices = index_ivf.search(query_vec, k=5)
```

**The trade-off:** searching fewer cells is faster but may miss the true nearest neighbours (approximate).

## nprobe Sweep and Recall@K

How does `nprobe` affect quality? We measure **recall@K**: what fraction of the true top-K (from exact search) does the approximate search recover?

| nprobe | recall@5 | Speed |
|---|---|---|
| 1 | ~0.34 | Fastest |
| 4 | ~0.67 | Fast |
| 16 | ~0.87 | Moderate |
| 32 | ~0.94 | Slower |
| nlist (50) | ~1.00 | Same as exact |

## Save and Load

FAISS indexes can be serialized to disk and reloaded:

```python
# Save
faiss.write_index(index, "quran_search.faiss")

# Load
index = faiss.read_index("quran_search.faiss")
```

Important: FAISS stores only vectors, not metadata. Always save the corresponding DataFrame separately and align by index position.

## QuranSearchEngine Class

The notebook wraps the full pipeline into a reusable class:

```python
class QuranSearchEngine:
    def __init__(self, df, model, index):
        self.df    = df
        self.model = model
        self.index = index

    def search(self, query, k=5, surah_filter=None):
        qvec = self.model.encode([query], normalize_embeddings=True).astype('float32')
        scores, indices = self.index.search(np.ascontiguousarray(qvec), k)
        results = []
        for idx, score in zip(indices[0], scores[0]):
            row = self.df.iloc[idx]
            if surah_filter and row['Surah'] != surah_filter:
                continue
            results.append({
                'verse_id': row['verse_id'],
                'text': row['daryabadi'],
                'score': float(score),
            })
        return results
```

The `surah_filter` parameter demonstrates **metadata filtering** — FAISS doesn't natively support filtered search, so we filter results post-hoc.

---

## Limitations

**1. Metadata filtering is a workaround**
FAISS stores only vectors. Filtering by Surah, topic, or any other attribute requires post-processing the results — you retrieve more than you need, then filter. Production vector databases (Pinecone, Weaviate, Qdrant) handle metadata natively.

**2. No update without rebuild**
Adding new documents to a trained IVF index requires retraining. For frequently updated corpora, this is expensive.

**3. Still returns passages, not answers**
FAISS retrieves the most similar passages — but a user asking a question wants a direct answer, not 5 paragraphs to read. That is what RAG solves.

## Reflection Questions

1. recall@K = 0.34 at nprobe=1 means FAISS missed 66% of the true top-K. Why would you ever use nprobe=1 in production?
2. `IndexIVFFlat` requires training before adding vectors. What does training do? Why doesn't `IndexFlatIP` need it?
3. FAISS `IndexFlatIP` uses inner product. Why do we normalize vectors before adding them?
4. You save the FAISS index but not the DataFrame of metadata. What breaks if you load the index without the matching DataFrame?
5. The `QuranSearchEngine` stores metadata in a Python dict. What would break if documents were added to the index after the class was initialized?
