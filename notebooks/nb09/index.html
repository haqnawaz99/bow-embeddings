    Upgrading the Baseline¶

    Every weakness listed in NB08's "What This Is NOT" section becomes a lesson here. Seven upgrades are applied to the naive RAG baseline, each measured against the previous approach.

    NB08 Baseline NB09 Upgrade
    Dense-only retrieval (SBERT) Hybrid: BM25 + SBERT fused with RRF
    No re-ranking Cross-encoder re-ranking of top-20
    Plain query as-is Query expansion via HyDE
    Full verse as retrieval unit Sentence-boundary chunking with overlap
    Full context to LLM Contextual compression
    No evaluation RAGAS-style faithfulness + relevance
    No comparison Side-by-side: naive vs advanced on 3 queries

    Section 2: Hybrid Retrieval (BM25 + SBERT + RRF)¶

    Why hybrid?¶

    BM25 is a sparse keyword-based ranker. It excels when the query uses the exact words that appear in the document — great recall for exact terminology, fast to compute, no GPU needed.

    SBERT is dense semantic search. It finds "compassion" when you query "mercy" because it encodes meaning into a vector space.

    Neither is perfect alone: - BM25 misses paraphrases ("forgiveness" vs "pardon") - SBERT can miss rare exact-match terms or proper nouns

    Reciprocal Rank Fusion (RRF)¶

    RRF combines multiple ranked lists without requiring score normalization:

    score(document) = sum over systems of  1 / (k + rank(document))

    Where k=60 is a smoothing constant. A document ranked 1st by both systems gets 1/61 + 1/61 = 0.033. A document only ranked 1st by one system gets 1/61 ≈ 0.016.

    def rrf_score(rank, k=60):
    return 1.0 / (k + rank)

def hybrid_retrieve(query, top_k=4):
    # BM25 leg
    bm25_scores = bm25.get_scores(tokenize_for_bm25(query))
    bm25_top = np.argsort(bm25_scores)[::-1][:20]

    # Dense leg
    qvec = encode_query(query)
    _, dense_top = index_flat.search(qvec, 20)

    # RRF fusion
    rrf = {}
    for rank, idx in enumerate(bm25_top, 1):
        rrf[idx] = rrf.get(idx, 0.0) + rrf_score(rank)
    for rank, idx in enumerate(dense_top[0], 1):
        rrf[idx] = rrf.get(idx, 0.0) + rrf_score(rank)

    ranked = sorted(rrf.items(), key=lambda x: x[1], reverse=True)[:top_k]
    return [build_result(idx, score) for idx, score in ranked]

    Section 3: Cross-Encoder Re-ranking¶

    Bi-encoder vs Cross-encoder¶

    A bi-encoder (SBERT) encodes query and document independently into vectors and uses cosine similarity. Fast and scalable — you pre-compute all document vectors. But the representations are computed in isolation — the model never sees query and document together.

    A cross-encoder reads query and document jointly in a single forward pass. It can model complex interactions between them — much more accurate. The cost: you cannot pre-compute document vectors, so it is too slow for initial retrieval over millions of documents.

    Two-stage pipeline¶

    Query
  |
  v
[Bi-encoder recall] → top-20 candidates (fast)
  |
  v
[Cross-encoder re-rank] → top-4 (accurate)
  |
  v
Final ranked results

    cross_encoder = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query, candidates, top_k=4):
    pairs = [(query, c["text"]) for c in candidates]
    ce_scores = cross_encoder.predict(pairs)
    for c, s in zip(candidates, ce_scores):
        c["ce_score"] = float(s)
    return sorted(candidates, key=lambda x: x["ce_score"], reverse=True)[:top_k]

    The rank shift analysis shows how the cross-encoder reorders candidates from the hybrid retrieval — some verses jump from rank 15 to rank 1, others drop.

    Section 4: HyDE — Query Expansion¶

    The Problem with Short Queries¶

    A query like "mercy for believers" is sparse — only a few tokens. The embedding may not capture the full semantic space of relevant documents.

    HyDE's Solution¶

    HyDE (Hypothetical Document Embedding, Gao et al. 2022):

    1. Use an LLM to generate a hypothetical answer to the query
    2. Embed the hypothetical document instead of the raw query
    3. The hypothetical doc is richer in vocabulary, covers synonyms, and sits closer in the embedding space to real relevant documents
    def hyde_retrieve(query, k=4):
    # Step 1: generate a hypothetical answer
    hyde_prompt = "Write a short passage that answers: " + query
    hypo_doc = generate(hyde_prompt)

    # Step 2: embed the hypothetical doc, not the raw query
    hypo_vec = encode(hypo_doc)
    scores, indices = index_flat.search(hypo_vec, k)
    return build_results(indices, scores)

    When HyDE helps: Queries with rare vocabulary, abstract concepts, or topics where synonyms are important.

    When HyDE fails: When the LLM generates a hallucinated hypothetical that points away from the real relevant documents; when the query is already precise and specific.

    Section 5: Sentence-Boundary Chunking¶

    Why Chunk?¶

    NB08 used the full verse as the retrieval unit. Long verses may contain multiple distinct topics — the retrieved text includes irrelevant sentences.

    Sentence-boundary chunking with overlap: - Split each verse into sentences using sent_tokenize - Group sentences into windows of CHUNK_SIZE=3 sentences - Overlap by CHUNK_OVERLAP=1 sentence so boundary sentences appear in two chunks

    def chunk_text(text, verse_id, chunk_size=3, overlap=1):
    sentences = sent_tokenize(text)
    step = max(1, chunk_size - overlap)
    chunks = []
    for start in range(0, len(sentences), step):
        chunk = sentences[start:start + chunk_size]
        if chunk:
            chunks.append({
                "verse_id": verse_id,
                "chunk_id": verse_id + "_c" + str(start),
                "text": " ".join(chunk),
            })
    return chunks

    Result: 2,500 verses → ~3,100 chunks. Chunk-level retrieval scores are higher because the retrieved unit is more focused.

    Verse-level vs chunk-level retrieval¶

    For the same query, chunk-level retrieval returns the most relevant sentence window within a verse — not the full verse padded with off-topic content.

    Section 6: Contextual Compression¶

    Even after chunking, a passage may contain sentences irrelevant to the query. Each irrelevant sentence: - Wastes LLM context tokens - Can distract the model into mixing relevant and irrelevant content - Increases hallucination risk

    Compression approach: 1. Split each retrieved passage into individual sentences 2. Score each sentence against the query using the cross-encoder 3. Keep only the top N sentences

    def compress_context(query, passages, top_n=2):
    compressed = []
    for p in passages:
        sentences = sent_tokenize(p["text"])
        if len(sentences) <= 1:
            compressed.append(p)
            continue
        scores = cross_encoder.predict([(query, s) for s in sentences])
        ranked = sorted(zip(scores, sentences), reverse=True)
        best = [s for _, s in ranked[:top_n]]
        new_p = dict(p)
        new_p["text"] = " ".join(best)
        compressed.append(new_p)
    return compressed

    Section 7: RAGAS-style Evaluation¶

    Why metrics matter¶

    Eyeballing answers is not scalable. Two failure modes: - Hallucination: answer makes claims not supported by the retrieved context - Irrelevance: answer is factually grounded but does not address the question

    Faithfulness score¶

    For each sentence in the answer, check whether it is entailed by at least one context passage. Score = max cross-encoder score across context passages.

    def faithfulness_score(answer, context_passages):
    sentences = sent_tokenize(answer)
    scores = []
    for sent in sentences:
        pairs = [(p["text"], sent) for p in context_passages]
        ce_scores = cross_encoder.predict(pairs)
        scores.append(float(max(ce_scores)))
    return round(sum(scores) / len(scores), 4)

    Answer relevance score¶

    def answer_relevance_score(query, answer):
    return round(float(cross_encoder.predict([(query, answer)])), 4)

    Interpreting CE scores

    Cross-encoder scores are raw logits — unbounded real numbers, not probabilities. A score of 3.5 does not mean "35% relevant". What matters is relative ordering: higher = more relevant for the same query. When comparing across queries, scores are not directly comparable.

    What We Built — What's Still Missing¶

    Techniques introduced in NB09¶

    Technique What it fixes
    Hybrid BM25+SBERT+RRF Dense-only misses exact-match terms
    Cross-encoder re-ranking Bi-encoder scores query/doc independently
    HyDE query expansion Short sparse queries miss paraphrases
    Sentence chunking with overlap Full-verse granularity includes noise
    Contextual compression Retrieved passages contain irrelevant sentences
    RAGAS-style evaluation No way to measure answer quality

    Still missing¶

    Gap Production solution
    Multi-hop reasoning Chain-of-thought RAG, iterative retrieval
    Conversation memory Sliding window, conversation summarization
    Streaming output Async generation, token streaming
    Safety filters Output classifiers, constitutional AI
    Retraining on domain Fine-tuning the encoder on your corpus

    Reflection Questions¶

    1. RRF uses k=60. What happens at k=1? What about k=1000?
    2. Why can the cross-encoder model richer query-document interactions than the bi-encoder?
    3. Describe two scenarios where HyDE would perform worse than vanilla dense retrieval.
    4. Contextual compression can remove too aggressively. What goes wrong when kept sentences lose their referential context?
    5. We use the cross-encoder for both re-ranking and evaluation. What are the risks of using the same model for both tasks?
